# AI 内容工业化平台｜开发总纲与实施基线

> 本文档是后续开发的最高优先级入口。其他文档如有冲突，以本文档、PRD、技术方案、ERD、API 文档的顺序为准。

## 1. 最终目标

建设一套 AI 原生内容工业化平台，让一个内容创作者可以在统一工作台中高效完成从小说文本到剧本、资产卡、AI Storyboard、镜头级图像/视频/语音生成、预览合成和项目资产沉淀的完整流程。

平台不是把传统影视团队的岗位搬到线上，也不是给编剧、美术、导演、制作、后期分别设计登录角色。传统岗位能力应沉淀为 AI Agent / AI 节点，创作者负责方向判断、结果确认、版本选择和必要修改。

## 2. 使用者模型

| 使用者类型 | 定位 |
|---|---|
| 内容创作者 | 平台核心用户，主导完整 AI 生产工作流 |
| 项目负责人 | 查看进度、成果、风险和成本；可由创作者兼任 |
| 平台管理员 | 维护模型、存储、队列、提示词模板、系统配置和成本策略 |

第一阶段只做项目访问控制，不做传统岗位权限体系。

## 3. 第一阶段开发目标

第一阶段必须先跑通最小闭环：

```text
创建项目
  → 输入小说文本
  → AI 小说分析
  → AI 剧本化改写
  → 生成并确认角色卡/场景卡/风格卡
  → 生成 AI Storyboard
  → 生成关键帧/参考图
  → 生成镜头级视频片段
  → 审核通过版本
  → 拼接简单预览
  → 沉淀项目资产
```

第一阶段不追求全自动无人审核、不做复杂 Agent 自主规划、不做复杂岗位权限、不做商业级专业剪辑、不做大规模资产市场。

## 4. 默认实施技术栈

| 层级 | 默认方案 |
|---|---|
| 前端 | Next.js + React + TypeScript |
| UI | Tailwind CSS + Ant Design |
| 后端 | FastAPI + Pydantic + SQLAlchemy |
| 数据库 | PostgreSQL + pgvector |
| 迁移 | Alembic |
| 队列 | Redis + Celery |
| 对象存储 | MinIO，兼容 S3 API |
| 媒体处理 | FFmpeg |
| 部署 | Docker Compose |

其他技术可以后续替换，但第一版不要并行实现多套技术路线。

## 5. 建议开发顺序

1. 工程骨架：`apps/web`、`services/api`、`services/worker`、`infra`。
2. 数据库迁移：用户、项目、小说、版本、资产卡、镜头、任务、媒体、模型、提示词。
3. 后端 API：先实现项目、小说、分析、剧本、资产卡、Storyboard、生成任务、媒体上传、审核。
4. Worker：先支持 mock 模型任务，再接真实文本、图像、视频、语音模型。
5. 前端工作台：围绕单个项目生产流程，不先做营销页或复杂后台。
6. 预览导出：先实现按通过镜头简单拼接，再扩展字幕、配音、BGM 和复杂剪辑。
7. 成本与监控：先记录模型调用和任务日志，再做预算预警和看板。

## 7. 开发时的硬约束

1. AI 生成结果不能直接覆盖正式版本，必须经过确认。
2. 每次模型调用必须记录模型、参数、提示词快照、耗时、状态和成本基础信息。
3. 媒体文件必须进入对象存储，数据库只保存元数据和引用。
4. 关键对象必须保留版本：分析、剧本、资产卡、镜头、生成结果、导出版本。
5. API 字段使用 `camelCase`，数据库字段使用 `snake_case`。
6. 第一版优先保证主流程闭环，不被复杂协同、复杂权限和复杂 Agent 编排拖慢。
